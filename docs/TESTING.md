# Testing

| Nivel | Herramienta | Dónde | Qué cubre |
|---|---|---|---|
| Unit backend | pytest | `backend/tests/unit/` | reglas puras: métricas, estados, scoring, normalización, configuración |
| Integración backend | pytest + PostgreSQL real | `backend/tests/integration/` | API + DB, migraciones, auth, imports (Fase 1) |
| Unit frontend | Vitest + Testing Library | `frontend/tests/` | componentes críticos, formularios, estados loading/empty/error |
| E2E | Playwright | `frontend/e2e/` | flujos críticos completos, desktop y móvil |

## Reglas
- Nunca SQLite: los tests de integración corren contra PostgreSQL (`TEST_DATABASE_URL`, base descartable que se migra desde cero en cada corrida).
- Reglas de negocio y métricas con TDD y fixtures verificables a mano (`METRICS.md §7`).
- Idempotencia de imports: test obligatorio desde Fase 1.
- Escenarios verificables a mano en `backend/tests/fixtures/` (por ejemplo `route_execution.py`: cumplimiento 66,7 % vs. cobertura 75 %). Son la especificación ejecutable de fases futuras; un test unitario verifica que sus valores esperados coinciden con las definiciones de `METRICS.md`, y la fase que implemente la métrica los usa tal cual.
- No se saltean ni desactivan tests para llegar a verde.

## Cómo correr
```bash
# Backend (requiere PostgreSQL; ver README)
cd backend && uv run pytest
# Frontend
cd frontend && pnpm test
# E2E (levanta backend y frontend; requiere un admin creado, ver README)
cd frontend && pnpm e2e
```

## Fecha de negocio en tests
- El día de negocio (zona `America/Argentina/Buenos_Aires`, `business_today()`) se resuelve **en el momento de usarlo**, dentro del test, fixture o helper; nunca en una constante de módulo (`T = business_today()`, `DAY = …`, `ISSUED = T - timedelta(days=12)`) ni en un default de argumento (`on: date = T`). Una constante se evalúa al importar: si la corrida cruza la medianoche de Buenos Aires, los tests mandan "hoy" con la fecha de ayer y fallan en falso.
- En los tests de Rendiciones se usa `tests/modules/settlements/days.py`: `today()`, `yesterday()` y `days_ago(n)`. Las fechas derivadas son funciones (`def issued_on() -> date: return days_ago(12)`), los defaults son `on: date | None = None` con `if on is None: on = today()` adentro, y un `parametrize` con fechas pasa desplazamientos en días que el test convierte al correr. Si un test compara varias fechas derivadas, conviene tomar `t = today()` una vez al principio y derivar de ahí.
- `backend/tests/unit/test_settlements_test_days.py` lo garantiza: prueba con el reloj movido a través de la medianoche que `today()` cambia entre dos llamadas, y recorre con `ast` cada archivo de `tests/modules/settlements/` fallando si algo que corre al importar (asignaciones de módulo, defaults, decoradores, cuerpos de clase) lee el reloj (`business_today`, `date.today`, `datetime.now` o un helper de `days.py`, directo o a través de una función local).
- E2E: `businessDay(offset)` de `frontend/e2e/helpers.ts` se llama al usarlo (`const today = () => businessDay()`), nunca como constante del spec ni con el reloj local de la máquina (`cash`, `delivery` y `fuel` pasaron a `businessDay`).
